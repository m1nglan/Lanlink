# Lanlink 栈溢出根因复盘

> 结论先行：**一切"诡异"问题的根因，是 `main` 任务栈溢出**。不是 IDF bug、不是 PSRAM、不是链接效应、不是 esp_timer 竞态——所有这些都是栈溢出破坏内存后表现出的"受害者"假象。

## 一、根因（一句话）

`main` 任务默认栈只有 **3584 字节**，而 `I2sMic` 对象里的大数组 `m_raw[640]`（2560 字节）+ 主循环的 `pcm[640]`（1280 字节）压在栈上，合计 **3840 字节 > 3584**，函数一进入就栈溢出，越界破坏内存。

## 二、根因机制（为什么"WiFi 之前没创建 i2s"也会溢出）

C 编译器在**函数入口一次性分配整个栈帧**，不是"用到哪个变量才分配哪个"。

ESP32-S3（Xtensa）用 `entry a1, N` 指令，在 `app_main` 第一条指令就把栈指针一次性下移 N 字节。**N 是编译期算好的、整个函数所有局部变量的总和**，跟变量声明位置、运行时执行顺序无关。

所以：

- `I2sMic mic` 里的 `m_raw[640]`（2560B）和 `pcm[640]`（1280B）的**栈空间在 `app_main` 一进入就全部预留**（栈指针瞬间下移约 3952 字节）
- 即使 `mic.init()` 确实要等 WiFi 连上之后才执行，**栈指针早已越过 3584 的栈底**

两个概念要分清：

| | 发生时机 | 性质 |
|---|---|---|
| **栈空间分配**（栈指针下移） | 函数入口第一条指令 | 编译期定大小，一次性 |
| **对象构造**（init 写入数据） | 声明点 / 调用点 | 运行时，WiFi 之后 |

修复前后反汇编对比：

```
修复前: entry a1, ~3952   （m_raw 2560 + pcm 1280 + 其他）→ 3952 > 3584 → 一进 app_main 就溢出
修复后: entry a1, 112     （m_raw/pcm 都 static 挪到 .bss）→ 112 << 3584 → 安全
```

## 三、为什么栈溢出不报"栈溢出"，而是卡死 / Cache error

ESP32-S3 的栈溢出检测用**硬件 watchpoint 监视栈底最后 32 字节，且只在写入时触发**：

```c
// port.c
void vPortSetStackWatchpoint(void *pxStackStart) {
    esp_cpu_set_watchpoint(..., 32, ESP_CPU_WATCHPOINT_STORE);  // 只在【写】时触发
}
```

栈溢出是"**面破坏**"（越界踩坏栈底下方任意内存），而 watchpoint 是"**点监视**"（只盯栈底 32 字节）：

- **只开 i2s**：`m_raw` 被 `i2s_channel_read` 大量写入，恰好碰到栈底 32 字节 → 触发 watchpoint → 报"stack overflow"
- **WiFi + i2s**：i2s 在 WiFi 之后不运行，`m_raw` 没被写；WiFi 的栈写入恰好没碰到那 32 字节 → watchpoint 静默，但越界踩坏的是 WiFi 数据结构 → 表现为 WiFi 卡死 / Cache error

一句话：**栈溢出检测是"在栈底 32 字节设写陷阱"，栈溢出是"越界踩烂栈底外面"。只有踩到陷阱才报"栈溢出"，踩到别处就报成"受害者"（WiFi 卡死）的症状。**

## 四、历史问题真相

回顾 `problem.md` 记录的 v6.0.1 "三大问题"，本质都是同一个栈溢出：

| problem.md 记录 | 真相 |
|---|---|
| 问题 1：esp_timer 竞态崩溃 | 栈溢出破坏 esp_timer 数据，触发 `vTaskGenericNotifyGiveFromISR` 断言 |
| 问题 2：PSA 互斥锁崩溃 | 栈溢出破坏 mbedtls/PSA 数据 |
| 问题 3：射频间歇失灵 | 板子陶瓷天线，**这个是真实的硬件问题**，与栈溢出无关 |
| v6.0.2 "链接效应"卡死 | 栈溢出破坏 WiFi 扫描数据结构 |

之前所有的"缓解措施"（WiFi 任务核1、关省电、`psa_crypto_init`、关 PM、禁断言、关 PSRAM、改 esp_timer 亲和性、关 IRAM_OPT）**全是伪修复**——它们只是改变了栈溢出破坏的位置，让症状从"崩溃"变成"卡死"或换一个受害者，根因一直都在。

## 五、修复方案

### 代码（根治：大缓冲移出栈）

1. `main/drivers/i2s_mic.hpp` — 删除成员 `uint32_t m_raw[I2S_MIC_FRAME_BYTES / 2]`（2560B 栈对象）
2. `main/drivers/i2s_mic.cpp` — `read_frame()` 改用 `static uint32_t raw[...]`（进 .bss）
3. `main/main.cpp` — `pcm[640]` 改为 `static`（进 .bss）

### 配置（余量：增大 main 任务栈）

```ini
# sdkconfig.defaults
CONFIG_ESP_MAIN_TASK_STACK_SIZE=8192
```

## 六、经验教训

1. **大缓冲（>1KB）永远不要放栈上**，用 `static` 或 `malloc`。栈是稀缺资源，默认 main 栈只有 3.5KB。
2. **栈溢出的症状是"随机内存破坏"**，指向的是受害者不是凶手。看到"卡死 / 崩溃 / 奇怪数据"时，第一反应先查栈（`uxTaskGetStackHighWaterMark` 或看反汇编的 `entry a1, N`）。
3. **栈帧大小编译期就定死**，函数入口一次性分配，与变量声明位置无关——别以为"这个对象后面才创建，栈就不会现在溢出"。
4. **栈溢出检测（watchpoint）是点监视**，不一定能逮到。越界没踩到监视点就静默破坏别人内存。
5. **配置排查要保留"对照"意识**：关一个配置后症状变化，只能说明"改变了破坏位置"，不能说明"找到了根因"。真正的根因（栈溢出）始终要回到内存/栈这个源头。
6. 一个 bug 修一周，往往根因是某个很基础的东西（一行栈大小 + 大数组放错位置），而不是复杂猜测。
